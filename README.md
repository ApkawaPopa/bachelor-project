# amina — приватный веб-мессенджер со сквозным шифрованием

**amina** — это современный веб-мессенджер, спроектированный с приоритетом безопасности и приватности. Вся передаваемая
информация (текст, файлы, метаданные) шифруется **на стороне клиента**. Серверная часть не имеет доступа к содержимому
сообщений, файлам или ключам шифрования — даже при компрометации сервера переписка остаётся защищённой.

---

## Стек технологий

### Бэкенд

- **Spring Boot 4** — основной фреймворк.
- **Spring Security** — аутентификация и авторизация (JWT + фильтры).
- **Spring Data JPA** — работа с PostgreSQL.
- **Spring WebSocket / STOMP** — двунаправленный обмен сообщениями в реальном времени.
- **Spring Web** — REST API.
- **PostgreSQL 18** — реляционная база данных.
- **RabbitMQ 4** — брокер сообщений с плагинами STOMP (используется как relay для WebSocket).
- **MinIO (AIStor)** — S3-совместимое хранилище файлов.
- **Caddy 2** — обратный прокси с автоматическим получением SSL-сертификатов.

### Фронтенд

- **Vue 3** — реактивный интерфейс (Composition API).
- **Vite** — сборка и разработка.
- **SockJS** + **STOMP.js** — WebSocket-клиент для обмена сообщениями.
- **Web Crypto API** — вся криптография выполняется в браузере: генерация RSA-ключей, симметричное шифрование AES-GCM,
  хеширование PBKDF2, импорт/экспорт ключей.

### Оркестрация

- **Docker** и **Docker Compose** — все сервисы запускаются как контейнеры.

## Функциональные возможности

### Аутентификация и управление ключами

- **Регистрация** — пользователь вводит логин и пароль. На клиенте генерируется **соль (16 байт)** и вычисляется хеш
  пароля через **PBKDF2** (600 000 итераций, SHA-256). Хеш передаётся на сервер, где повторно хешируется **BCrypt** и
  сохраняется вместе с солью.
- **Вход** — аналогично: клиент запрашивает соль пользователя, вычисляет хеш пароля и отправляет на сервер. Сервер
  сравнивает с сохранённым BCrypt-хешем.
- **RSA-ключи** — при регистрации генерируется пара **RSA-4096**. Публичный ключ (в формате JWK) сохраняется на сервере
  открыто. Приватный ключ экспортируется в PKCS#8, **шифруется** с использованием пароля пользователя (AES-GCM) и
  сохраняется на сервере в зашифрованном виде. Расшифровка происходит только на клиенте при входе.
- **JWT** — после успешной аутентификации выдаётся JWT (HMAC-SHA256), который используется для REST API.
- **WebSocket-токены** — для подключения к WebSocket используется **одноразовый UUID-токен**, выдаваемый после
  предъявления JWT. Это предотвращает несанкционированные подключения.

### Чаты и сообщения

- **Создание групповых чатов** — пользователь указывает название и список участников. Для чата генерируется **AES-256**
  ключ (симметричный). Ключ шифруется отдельно для каждого участника с использованием его публичного RSA-ключа.
  Зашифрованные копии сохраняются в связке `user_chat`.
- **Отправка сообщений** — текст шифруется на клиенте с помощью **AES-GCM** (используется ключ чата) и отправляется
  через STOMP. Получатели расшифровывают сообщения своим экземпляром симметричного ключа.
- **Редактирование и удаление** — поддерживается редактирование и удаление собственных сообщений (удаление также удаляет
  прикреплённые файлы из S3). Участники получают соответствующие события через WebSocket.
- **Статус прочтения** — когда пользователь открывает чат, автоматически отправляется подтверждение прочтения для
  каждого сообщения. Сервер сохраняет факт прочтения в таблице `message_receiver`.
- **История сообщений** — все сообщения хранятся в зашифрованном виде в БД. При загрузке чата клиент получает список
  сообщений и расшифровывает их локально.
- **Уведомления о непрочитанных** — при получении нового сообщения всем участникам (кроме отправителя) отправляется
  счётчик непрочитанных.

### Файлы и вложения

- **Загрузка файлов** — до 15 файлов на одно сообщение. Каждый файл шифруется **AES-GCM** перед отправкой в MinIO. Имя
  файла также шифруется (отдельно от содержимого).
- **Процесс загрузки**:
  1. Клиент шифрует имя файла и отправляет список зашифрованных имён на `/api/v1/s3/upload-urls`.
  2. Сервер создаёт запись в БД (S3Object) с зашифрованным именем, возвращает подписанный URL на загрузку и числовой
     идентификатор объекта.
  3. Клиент загружает зашифрованное содержимое файла по этому URL (PUT).
  4. При отправке сообщения клиент передаёт список идентификаторов объектов, после чего они привязываются к сообщению.
- **Скачивание** — клиент запрашивает подписанные URL для скачивания, затем загружает зашифрованный объект и
  расшифровывает его локально.
- **Файлы в сообщениях** — отображаются как вложения; изображения показываются миниатюрами прямо в тексте сообщения.

### Визуальное оформление

- **Аватарки чатов** — можно установить любое изображение в качестве аватарки чата. Изображение шифруется и сохраняется
  как файл, ссылка на него доступна всем участникам.
- **Аватарки пользователей** — аналогично, каждый пользователь может установить свои аватарки (несколько). Последняя
  загруженная считается текущей.
- **Галерея изображений** — все изображения чата можно просматривать в виде карусели.

### Безопасность и приватность

- **Полное сквозное шифрование** — сервер не имеет доступа к открытому тексту сообщений, ключам и содержимому файлов.
- **Сравнение ключей** — в меню чата отображается визуальный «отпечаток» (матрица пикселей и строки), создаваемый из
  хеша ключей всех участников. Все пользователи могут визуально убедиться, что у них одинаковый ключ, что гарантирует
  отсутствие подмены.
- **Защита от повторного использования ключей** — каждый объект S3 может быть подтверждён (привязан к сообщению или
  аватарке) только один раз.
- **Очистка неподтверждённых объектов** — регулярный джоб удаляет файлы, загруженные, но не привязанные к сообщению,
  спустя час.

### Обмен сообщениями в реальном времени

- WebSocket-соединение устанавливается через **SockJS** с одноразовым токеном.
- **STOMP-релей** на RabbitMQ обеспечивает масштабируемую доставку сообщений между участниками.
- Подписка на каналы чата (`/topic/chat.{id}`) и пользовательские очереди (`/user/queue/...`) для персонализированных
  уведомлений.

## Развёртывание на собственном оборудовании

### Предварительные требования

- Установленные **Docker** и **Docker Compose** (поддерживающие синтаксис version 3).
- Доступные порты **80** и **443** на хост-машине (для Caddy).

### 1. Получение исходного кода

Склонируйте репозиторий и перейдите в склонированную папку.

### 2. Настройка переменных окружения

Скопируйте пример конфигурации и при необходимости отредактируйте:

```bash
cp .env.example .env
```

**Основные переменные:**

- `ADDRESS` — внешний адрес приложения (по умолчанию `localhost`). При указании домена Caddy автоматически получит Let's
  Encrypt сертификат. Для `localhost` и ip-адресов используется самоподписанный сертификат.
- `BACKEND_JWT_SECRET` — секретный ключ для JWT (обязательно смените на свой).
- `POSTGRES_PASSWORD` — пароль базы данных.
- `S3_ROOT_PASSWORD`, `S3_ACCESS_KEY`, `S3_SECRET_KEY` — учётные данные MinIO (рекомендуется изменить).
- `BROKER_LOGIN`, `BROKER_PASSCODE` — учётные данные RabbitMQ.

### 3. Запуск всех сервисов
```bash
docker compose up -d --build
```

- После успешного запуска приложение будет доступно по адресу **https://localhost** (или по вашему `ADDRESS`).

### 4. Остановка
```bash
docker compose down
```

### 5. Изменение портов и адресов

- В файле `docker-compose.env` можно изменить `POSTGRES_PORT` (по умолчанию `43121`) для доступа к БД извне.
